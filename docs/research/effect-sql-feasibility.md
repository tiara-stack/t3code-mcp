# Effect SQL and shared SQLite feasibility

Investigated 2026-09-19 for [Choose Effect service boundaries, recovery, and design validation](https://linear.app/tiara-stack/issue/TIA-266/choose-effect-service-boundaries-recovery-and-design-validation). This is source research, not a runtime experiment. The findings use published `4.0.0-rc.115` package sources, matching the repository's Effect version.

## Package and API choice

Use `@effect/sql-sqlite-node@4.0.0-rc.115`. Its published peer dependency is `effect: ^4.0.0-rc.115`. It implements Effect SQL through Node's built-in `node:sqlite`. Generic application SQL uses `effect/unstable/sql/SqlClient`; migrations use `@effect/sql-sqlite-node/SqliteMigrator`. The driver's `SqliteClient.layer` provides both generic and SQLite-specific clients. [Published package metadata](https://registry.npmjs.org/@effect/sql-sqlite-node/4.0.0-rc.115), [published source archive](https://registry.npmjs.org/@effect/sql-sqlite-node/-/sql-sqlite-node-4.0.0-rc.115.tgz)

`SqliteMigrator.run` applies migrations and returns their IDs and names. `SqliteMigrator.layer` runs them during layer construction. Both use `effect/unstable/sql/Migrator`, whose `fromRecord` accepts migration effects keyed by `<id>_<name>` and orders them by ID. A bundled record avoids runtime directory discovery in the packaged executable. SQL and migration effects remain behind the local-store layer; MCP handlers need no SQL dependency. [SQLite migrator source](https://unpkg.com/@effect/sql-sqlite-node@4.0.0-rc.115/src/SqliteMigrator.ts), [shared migrator source](https://unpkg.com/effect@4.0.0-rc.115/src/unstable/sql/Migrator.ts)

## Startup and concurrency

The pinned driver enables WAL by default, configures a five-second `busyTimeout`, and uses `BEGIN IMMEDIATE` for writable `withTransaction` calls. Create the application SqliteClient.layer with busyTimeout: 0 before providing that client to SqliteMigrator.layer or SqliteMigrator.run. Do not defer the override to a pragma executed after client initialization or migration. Its semaphore serializes use of its own connection only. Even explicit transactions that only read acquire the write transaction on a writable client. Connection creation and initial pragmas can throw defects because `make` exposes no typed error; the store's startup boundary must translate expected open/configuration failures. [Pinned driver source](https://unpkg.com/@effect/sql-sqlite-node@4.0.0-rc.115/src/SqliteClient.ts)

The shared migrator creates its ledger with `CREATE TABLE IF NOT EXISTS`, then reads migration state, inserts pending ledger entries, and executes the migration effects in `sql.withTransaction`. The SQLite driver therefore takes the database write transaction before reading that state. This is the source-level basis for concurrent startup serialization. Ledger creation happens outside that transaction and may itself encounter contention. The shared migrator also converts its `Locked` migration error to an empty result, so successful return alone should not be the readiness check. [Shared migrator source](https://unpkg.com/effect@4.0.0-rc.115/src/unstable/sql/Migrator.ts)

Design inference: gate each process's readiness on completed configuration, migration, and an explicit supported-schema check. Bound startup contention retries and return a diagnosable startup failure when exhausted. After migration, verify the expected journal and target schema explicitly; reject both older and newer unsupported schemas before readiness. While different executable versions share a store, migrations must preserve the supported older readers and writers; incompatible upgrades require stopping those processes first. Keep migrations SQL-only and local. Do not hold a database transaction across an RPC. SQLite transaction locks provide brief storage serialization without persistent resource ownership rows or leases. A terminated process must never leave a logical resource gate behind. [SQLite transactions](https://www.sqlite.org/lang_transaction.html)

## Durability and runtime constraints

Set and verify `journal_mode=WAL`, `synchronous=FULL`, and `busyTimeout=0` on each writable connection before admitting operations. Enforce the finite five-second contention budget through Effect-scheduled retries, not a synchronous driver wait. FULL syncs WAL commits; NORMAL can lose committed state on power failure. WAL requires local disk on the same host and still permits only one writer. Keep transactions short, including capture eviction and retention. Protect the database directory and its WAL/SHM files with the agreed owner-only permissions. [SQLite WAL](https://www.sqlite.org/wal.html), [SQLite pragmas](https://www.sqlite.org/pragma.html)

The chosen driver uses synchronous Node SQLite calls, so its default busy wait can block the process's event loop. Override busyTimeout to zero and use Effect-scheduled jittered retry from 25 ms to 250 ms for local SQLITE_BUSY failures, preserving the design's total five-second contention budget. Release the failed attempt's transaction and connection permit before backoff; retry only local work known to have rolled back, never RPC effects or ambiguous commits. This is the selected application policy, not the driver's default. An Effect timeout alone cannot preempt a synchronous SQLite call. [Node SQLite documentation](https://nodejs.org/download/release/v24.11.0/docs/api/sqlite.html), [pinned driver source](https://unpkg.com/@effect/sql-sqlite-node@4.0.0-rc.115/src/SqliteClient.ts)

Require an embedded SQLite build containing the WAL-reset race fix before enabling shared WAL storage. SQLite identifies the fix in 3.51.3 and later, with backports in 3.44.6 and 3.50.7. The race affects concurrent connections writing or checkpointing the same WAL database. The repository's Node lower bound alone does not establish this property; select and test a supported Node release and check `sqlite_version()` or an explicitly verified vendor backport. [SQLite WAL-reset bug](https://www.sqlite.org/wal.html#the_wal_reset_bug)

## Validation still required

No package was installed into this repository, and no SQL or multiprocess experiment was run for this note. Implementation acceptance must exercise simultaneous first startup and upgrade, kill during migration and admission, bounded busy failures, duplicate request IDs across processes, rollback after disk failures, schema compatibility rejection, and restart with existing WAL files. Hold a write transaction in another process while issuing concurrent MCP calls; verify that scheduled contention retries preserve unrelated-call, cancellation, and deadline responsiveness. Verify configured pragmas and embedded SQLite version in those tests. Remote mutations remain outside SQLite atomicity; recovery reads evidence and never takes over dispatch or replays an unfinished operation.
