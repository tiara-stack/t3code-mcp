# T3Code V2 tool alignment for a multi-instance controlling agent

Research for [TIA-321](https://linear.app/tiara-stack/issue/TIA-321/compare-native-v2-tools-with-the-multi-instance-controlling-agent). This is an inventory and decision input, not a public-tool naming decision or an implementation plan.

Other MCP toolkits (preview, attachment, HTML, device, pull request) exist but are outside this comparison. The design document still says "eleven orchestration tools"; definitions and registrations show 17 in the release and 18 at main, so the source definitions and handlers govern this inventory. The design's sample `delegate_task` target also omits the implemented `options` and `isolation` fields. [Release definitions][release-orchestrator] · [main definitions][main-orchestrator-tools] · [MCP registration][main-registration] · [design text][main-design]

The release and main share the core `delegate_task`, `create_threads`, `t3_thread_*`, project, queue, pending-request, and worktree names. Material observed differences: main adds `t3_background_wait`; ready-made optional `link` appears in delegated-task, created-thread, thread-list/read/send, and `t3_thread_launch` results; `next` appears in delegated-task and thread-wait results; `request_secret` adds a `delivery: "file"` branch; and `t3_thread_search` changes its result shape. Main documentation permits a `t3_thread_send` follow-up to a completed child's `childThreadId` as a **fresh task**, whereas release documentation explicitly says to start a new `delegate_task` round. Neither reopens the original task result. These differences need a target-version decision elsewhere. ## Identity, scope, and completion guarantees

**Environment is not provider.** A native provider-session MCP credential binds `environmentId` plus `threadId`, `providerSessionId`, and `providerInstanceId`; its `requestNamespace` is the provider session ID. An external OAuth MCP client has a client `sessionId`, access ceiling, and namespace `client:<sessionId>`, but no calling `thread`. A provider-instance ID chooses a model adapter *within one environment*; it is not this server's `instanceId` registration and cannot stand in for a parent thread/session identity. [Invocation scope][main-invocation] · [provider credential registry][main-session-registry] · [client auth][main-client-auth]

Handlers mark `delegate_task`, `task_status`, `task_cancel`, `create_threads`, `request_secret`, `t3_background_wait`, `t3_worktree_handoff`, and `t3_worktree_status` as caller-thread operations. In particular, `delegate_task` checks a live parent run with the credential's provider instance and records a parent-owned child task. A controller outside a T3 thread cannot supply those facts by argument; a native `t3_thread_launch` can create an ordinary top-level thread under an external client's approved mode ceiling, provided it supplies `projectId` or `scratch`. Its `workspaceStrategy` defaults to the **project root**, not a caller worktree. [Handlers][main-orchestrator-handlers] · [access gates][main-access] · [delegation check][main-orchestrator-service] · [launch handler][main-project-handlers] · [worktree handlers][main-worktree-handlers]

Other native reads and writes can address any target thread **within the authenticated environment** subject to capability, caller liveness, and mode ceilings. `t3_thread_list` pages a named project; `t3_thread_read` and `t3_thread_send` can address another project's thread by its ID. A [service test][main-activity-test] exercises cross-project read and send. Native tool arguments do not contain a T3 environment selector: a multi-instance controller must route to the right endpoint/credential and preserve its local registration identity separately. [Access gates][main-access] · [thread access][main-thread-access] · [contract][main-contract]

V2 distinguishes **run**, **delegated task**, **thread**, **workflow**, and **provider session**. A run can be `preparing`, `queued`, `starting`, `running`, `waiting`, `completed`, `interrupted`, `failed`, `cancelled`, or `rolled_back`. `t3_thread_wait` reports a selected run's durable status, not controller work completion. `task_status.workState` distinguishes a child whose turn ended but whose nested work remains from one with a result. `task_cancel` stops the child thread and its nested tasks; `t3_thread_interrupt` targets an active run; V2 internal `thread.stop` also holds queued work and ends watches. None is a rename of the old `thread_stop_session`, which requests provider-session shutdown. [Run status][main-v2-contract] · [task contract][main-contract] · [V2 stop command][main-v2-contract] · [stop tests][main-stop-tests] · [old context][old-context]

**Request IDs are not interchangeable.** The old server requires a global `requestId` on every mutation, persists admitted-operation receipts across process restart, supplies `operation_get`, refuses changed payloads under an existing ID, retains details 30 days and tombstones for the database lifetime. Native `clientRequestId` is optional on selected tools only. The V2 service derives command/message/thread IDs from `(requestNamespace, operation, clientRequestId[, index])`: the namespace is provider-session or OAuth-client-session scoped. Calls without one receive a generated key. `t3_thread_launch` and many queue/organize/project tools have no such input. The inspected native MCP schemas have no general `operation_get` or equivalent local receipt/tombstone contract. A V2 adapter must keep the old SQLite registrations, mutation receipts, and captured history readable and migrate their data, while defining how new native command IDs correlate with local receipts; replacing the ID contract with native retry keys would lose the old guarantee. This is a requirement for the later design, not an implementation prescription. [Old README][old-readme] · [old store][old-store] · [native ID construction][main-orchestrator-service] · [native schemas][main-contract] · [launch tool][main-project-tools]

**Output bounds differ.** The old `thread_output`/`diff_read` inputs use byte budgets (default 16 KiB, max 64 KiB) and opaque retained capture cursors; the server caps serialized tool results at 128 KiB. Native `t3_thread_read` uses durable timeline `afterPosition`/`nextPosition` and per-item `textOffset`/`nextTextOffset`, with limits of 100 items, 50 recent runs, and 50,000 characters *per item*. `t3_queue_list` truncates each item to 1,000 characters and `t3_queue_read` to 16,000. There is no native MCP `diff_read` byte cursor. Old waits cap at 30 seconds and can wait for an explicit state condition or exact observed turn; native `t3_thread_wait` caps `timeoutMs` at one hour in the service and waits for run terminality. ## All 27 existing tools mapped

Ratings judge the **whole existing tool contract**, including instance qualification, output envelope and recovery: **E** equivalent, **P** partial, **A** absent from native MCP, **C** context-restricted. A native action can be useful while the whole tool remains partial. No row is E at the whole-contract level because every existing targeted call is instance-qualified and all existing mutations have durable local `requestId` semantics; native tools operate at one authenticated environment and do not share that receipt contract. ## Naming and semantic conflicts for the human toolkit decision

1. **Same noun, different authority:** `instance_*` addresses this repository's persistent connection records; `t3_environment_*` addresses one native environment; `providerInstanceId` is a model-provider selection inside it. Preserve separate identities. [Old context][old-context] · [native scope][main-invocation]
2. **`thread_create`, `create_threads`, `t3_thread_launch`, and `delegate_task` are different:** old creation is idle and instance-qualified; native batch creation is top-level but parent-context-only; launch can be idle or prompt-bearing with a workspace strategy; delegation creates a parent-owned child task and completion delivery. Reusing a name across these operations would hide lineage or workspace differences. [Old contract][old-contract] · [native contract][main-contract] · [launch tool][main-project-tools]
3. **`thread_submit` versus `t3_thread_send`:** native `auto` can steer or queue depending on state, `restart` interrupts and restarts, and the acknowledgement includes a run/message. Old submission has explicit intent/context and can complete as *submission accepted* with no established turn correlation. [Old contract][old-contract] · [native contract][main-contract]
4. **`thread_wait`/`turn_wait` versus `t3_thread_wait`:** native run terminality and ID are different from old condition-plus-cursor waiting and exact 0.0.45 turn references. A native wait timeout does not mean work stopped; neither wait means the controlling agent is done. [Old context][old-context] · [native contract][main-contract]
5. **`thread_interrupt`, `thread_stop_session`, `task_cancel`, `t3_workflow_stop`, and V2 `thread.stop`:** each acts at a different lifecycle scope. Do not alias one to another without choosing the promised side effects and guards. [Old context][old-context] · [native tools][main-orchestrator-tools] · [V2 command][main-v2-contract]
6. **`thread_get`/`thread_output` versus `t3_thread_read`:** native read combines shell, runs and paged timeline, and may acknowledge an app-owned child result. Old output capture has byte budgets and retained opaque cursors. The same name could overpromise passive reads or old cursor behavior. [Old contract][old-contract] · [native read service][main-orchestrator-service]
7. **`worktree_list/create/discard` versus `t3_worktree_list/status/handoff`:** native MCP worktree tools are anchored to a thread's workspace or the calling thread, and none implements explicit guarded discard. Launch's workspace creation is coupled to a thread. [Old context][old-context] · [worktree tools][main-worktree-tools] · [launch tool][main-project-tools]
8. **`approval_respond` versus `t3_pending_request_respond`:** the latter only answers user questions; similar request IDs do not confer permission-approval authority. [Native pending tool][main-thread-tools] · [old contract][old-contract]
9. **`requestId` versus `clientRequestId`:** global persistent local recovery and per-session native command deduplication have different scopes, coverage and lookup behavior. An API name match cannot imply the old recovery guarantee. [Old README][old-readme] · [native ID construction][main-orchestrator-service]
10. **`model_list` versus `orchestrator_capabilities`:** the native tool advertises provider instances and a deliberately abbreviated model catalog for delegation; it does not list T3 environments or guarantee a complete paged model list. [Native contract][main-contract] · [old schema][old-schemas]

## Open decisions and evidence limits

- Which immutable V2 release or later commit becomes the adapter target is left to the release-selection decision. The installed global `t3` CLI version and this parent session's injected tools were **not** treated as proof of the published native contract. This report inspects source snapshots; it does not run a disposable V2 instance, exercise OAuth/RPC authorization, or establish live compatibility. [Release][release-orchestrator] · [main registration][main-registration]
- The human toolkit decision needs to decide which native names can be exposed with their exact native meanings, which multi-instance wrappers retain separate names, and whether context-only operations should be omitted from the external toolkit or offered only in a T3-parent context. No public names or aliases are selected here.
- V2 RPCs expose ingredients for diffs, worktree removal, thread deletion, shell/timeline subscriptions, and stop, but source schemas alone do not prove the external credential can call them or that they preserve this server's old guards. External authorization and integration boundaries are separate research. [RPC methods][main-rpc] · [V2 RPC methods][main-v2-contract]
- Existing SQLite registrations, mutation receipts, and captured history must survive the upgrade even though no old API/V1 compatibility is required. The exact migration and recovery protocol is outside this research. [Old store][old-store] · [old README][old-readme]
- Tests were **read**, not executed. The inspected primary tests cover toolkit access restrictions, cross-project thread reads, native delegation/cancellation, and stop semantics, but deterministic adapters in the V2 integration suite do not prove behavior against every real provider or deployment. [Access tests][main-access-tests] · [integration test][main-integration-test] · [cancellation test][main-cancel-test] · [stop tests][main-stop-tests] · [design verification note][main-design]
