# External control of T3-owned child delegation

Researched 2026-10-26 02:36 UTC for [TIA-327](https://linear.app/tiara-stack/issue/TIA-327/investigate-a-supported-external-contract-for-t3-owned-child). This follows the completed [V2 external-contract report](https://github.com/tiara-stack/t3code-mcp/blob/27ab0f1f471abaea1bff0aa374407c06cb33111f/docs/research/t3code-v2-contracts.md) and [tool-alignment report](https://github.com/tiara-stack/t3code-mcp/blob/883b8e728c54080bf58f69a9aae63477b6d50262/docs/research/t3code-v2-tool-alignment.md) into upstream code and tests. The selected released baseline is T3Code `v0.1.2` at `044f07257c9684ae4543bd1e1ebf9c394e9e3830`, protocol 2. A fresh `git ls-remote` of `refs/heads/main` returned `fd71ddc223091093d172a431f4080772fa41c2a9` at 02:32 UTC; that is a source snapshot, not the selected release. GitHub's latest stable release API still returned `v0.1.2` at the time of this research. [Release][stable-release] · [main commit][main-commit]

## Finding

No complete, ownership-safe **external delegation contract** exists at either pin for a standalone controller to create, observe, and cancel a T3-owned child as its own task. The native `delegate_task`, `task_status`, and `task_cancel` tools act as a T3 parent thread. An external MCP OAuth client has no such thread in its invocation scope, even at `full-access`; the access test expects `thread_credential_required`. Creation also requires an active parent run whose provider instance matches the provider-session credential. This finding leaves the selected ordinary-thread WS/HTTP baseline intact. [Invocation scope][stable-invocation] · [tool handlers][stable-handlers] · [caller test][stable-access-test] · [parent gate][stable-parent-gate]

There is a narrower, easy-to-miss fact. The paired V2 WebSocket `orchestration.dispatchCommand` schema includes `delegated_task.request`. With a *real* active parent run and a node in that run, the low-level dispatcher can create an `app_owned` subagent, child thread, child run, and context transfer. The RPC policy asks for `orchestration:operate`, and the WebSocket handler forwards the command while stamping user provenance. This is source evidence that the command is exposed on the wire, not evidence of a supported standalone ownership model or a live interoperability result. [Command schema][stable-command] · [RPC scope][stable-rpc-auth] · [WS handler][stable-ws-dispatch] · [dispatcher][stable-low-level-dispatch] · [child and transfer][stable-low-level-child]

The distinction matters. The low-level command accepts caller-supplied `parentThreadId`, `parentRunId`, and `parentNodeId`. Its inspected gate checks that the run is active, has not reached Stop, and contains the node. It does **not** bind the paired client's identity to that parent, check that the client owns the parent run, or apply the native tool's child runtime and interaction mode ceiling. A client could therefore point at another active parent if it knows the IDs. Supplying real IDs avoids inventing a run, but it does not prove the outside controller has authority to speak as that parent. A command sequence alone is not a task-management grant. These are conclusions from the inspected admission paths; no live attempt was made. [Command schema][stable-command] · [RPC scope][stable-rpc-auth] · [WS handler][stable-ws-dispatch] · [dispatcher][stable-low-level-dispatch] · [native mode check][stable-native-mode]

## Released behavior and the controller-thread question

The stable `/mcp` endpoint accepts T3-issued provider-session registry credentials or separately approved MCP OAuth client sessions. Registry records bind an environment, thread, provider session, and provider instance; the raw token is sent to the provider session and the registry keeps its hash. A registry token fails after 24 hours of inactivity; an active provider turn can refresh its record, and session or thread release revokes it. The OAuth client session is a different audience: it is accepted only at `/mcp`, has a 30-day lifetime, and carries an approved access ceiling. Ordinary paired environment credentials enter `/ws` and HTTP, while MCP client sessions are rejected there. Neither copying nor fabricating a provider-session token is part of an external integration. [Registry][stable-registry] · [registry revocation][stable-registry-revoke] · [MCP middleware][stable-mcp-http] · [OAuth audience][stable-oauth-audience] · [OAuth session][stable-oauth-session] · [MCP auth test][stable-mcp-auth-test]

For native MCP, `read-only` grants `orchestration:read`; write access grants `orchestration:operate`, while `full-access` adds settings and source-control write scopes. Those scopes do not supply `scope.thread`. The handler first requires a thread caller, and `delegate_task` then finds that thread's active run and checks its provider instance. `task_status` only finds tasks on that same parent thread. `task_cancel` applies parent/child mode checks and stops the child and nested work; a returned `cancel_requested` is not terminal completion. [Access levels][stable-access-levels] · [caller guard][stable-caller-guard] · [parent gate][stable-parent-gate] · [task read][stable-task-read] · [task cancel][stable-task-cancel]

An outside client may launch an ordinary top-level T3 thread from a project, with an initial message that starts a run. The launched provider agent can legitimately call `delegate_task` using its own T3-issued credential while its run is active. The controller can ask it to do that and read its thread later. That is a documented *indirect* route through a real agent turn, with the task owned by that parent thread. The controller cannot invoke `delegate_task` as the launched thread through its external OAuth client or paired WebSocket credential, and a message asking the agent to delegate does not guarantee that it will. An idle launch has no active run. The top-level thread itself is not a delegated task. [External launch][stable-launch] · [native flow][stable-design] · [caller guard][stable-caller-guard] · [parent gate][stable-parent-gate]

A standalone controller must retain its own T3Code instance registration and route each request to that environment's endpoint and credential. `environmentId` in an MCP invocation names the T3 server; `providerInstanceId` selects a model provider *inside* that server. They are different identities. For a paired-session extension, `orchestration:operate` alone currently authorizes the whole `dispatchCommand` RPC, not a particular parent or task. A safe public delegation operation would need a scoped grant or an explicit server-side ownership check at admission and again at cancellation. Revoking a provider-session credential already follows the provider lifecycle; revoking an external controller's grant and deciding whether its existing children continue are separate, unspecified policies. [Invocation scope][stable-invocation] · [RPC scope][stable-rpc-auth] · [registry revocation][stable-registry-revoke] · [session revocation][stable-session-revoke]

## Task lifecycle evidence and missing external guarantees

- T3's native result contains `taskId` (a node ID), `childThreadId`, `childRunId`, status, `workState`, result summary, and a result context-transfer ID. `workState` distinguishes unfinished nested work from a result. The child thread is backing storage, while the parent's `app_owned` subagent projection and `subagent_result` transfer carry task identity and result. `task_status` is scoped to the parent and reading a terminal task can acknowledge completion delivery. The replay-based integration test exercises a child result, follow-up work, transfer IDs, and acknowledgement; it does not test an external client. [Result contract][stable-result-contract] · [task read][stable-task-read] · [result test][stable-result-test]
- Native `clientRequestId` is optional. T3 derives command IDs from a provider-session or MCP-client namespace, operation, and request key. With no key it generates one. The low-level WebSocket command requires a caller-supplied `commandId`; the durable command receipt can replay an accepted command's original sequence and events, but `dispatchCommand` returns only `{sequence}` and the inspected RPC set has no public receipt lookup by command ID. None of these alone gives this MCP server's persistent cross-restart mutation-receipt contract or a task lookup after a lost create response. [ID derivation][stable-id-derivation] · [receipt path][stable-receipt] · [wire result][stable-wire-result] · [RPC names][stable-rpc-names]
- A paired client can read parent and child V2 projections and subscribe to their streams. It could reconstruct some task state from subagent, run, and context-transfer rows. That is not `task_status`: no external owner-scoped task read, task wait, or task cancel RPC is declared. Sending raw `thread.stop` to the child is broader than `task_cancel`; the latter checks every nested target against the parent's modes, disposes pending delivery, and reports a task-specific outcome. [RPC names][stable-rpc-names] · [task read][stable-task-read] · [task cancel][stable-task-cancel] · [stop test][stable-stop-test]
- Once accepted, T3 persists the child and finalizes a terminal child from stored events; the design says that finalization recovers after a server restart. A controller process disconnect is therefore not itself a T3 task cancellation, an inference from storage and recovery code rather than a live disconnect test. A naturally ended parent turn can receive an async completion wake. Parent Stop or interrupt can dispose delivery and stop descendants; archived or deleted parents dispose delivery. A later contract must state what happens on controller exit, credential revocation, parent run completion, parent Stop, archive, and deletion separately. [Recovery and delivery][stable-design] · [stop test][stable-stop-test] · [delivery gate][stable-delivery-gate]

## Current-main check

At `fd71ddc223091093d172a431f4080772fa41c2a9`, `delegate_task`, `task_status`, and `task_cancel` remain `actsAsCaller`; the access test still denies a full-access external client; the service still requires an active run and matching provider instance. Main adds `t3_background_wait`, but it too acts as the calling thread. Main retains the caller-supplied parent IDs in `delegated_task.request`, the broad `dispatchCommand` scope, and the same active-run/node check. These are unreleased source observations relative to the selected `v0.1.2` baseline, not a reason to change that baseline. ## Smallest missing public contract

T3Code would need one explicit external delegation operation backed by its existing delegated-task machinery, plus owner-scoped task read and cancellation. This is a contract requirement, not a selected endpoint or implementation. At minimum it must:

1. Authenticate an external controller in one T3Code environment and establish a server-verified owner. If a launched controller thread is the parent, T3 must verify its real active run and node and define who may act for it. If work may outlive that run without a provider parent, T3 needs a durable external-owner or controller-run model instead. The caller must not assert arbitrary parent IDs as authority. [Current parent gate][stable-parent-gate] · [low-level command][stable-command]
2. Check the caller's project/thread grant, provider selection, child runtime and interaction ceiling, and revocation state when creating, reading, and cancelling. Preserve the existing target-provider enablement and nested cancellation checks. Identify the environment separately from the provider instance in this MCP server's references. [Native mode check][stable-native-mode] · [target enablement][stable-target-enablement] · [task cancel][stable-task-cancel]
3. Return stable `taskId`, `childThreadId`, and `childRunId`, and bind an idempotency key to the authenticated controller and request payload. Expose a durable lookup after a lost response. Define whether retrying after the parent turn ends returns the accepted task rather than failing the new active-run check. [Result contract][stable-result-contract] · [ID derivation][stable-id-derivation] · [receipt path][stable-receipt]
4. Expose owner-scoped status, bounded observation or wait, result and context-transfer acknowledgement, and task-specific cancellation with terminal outcomes. Define how pending questions and approvals surface without granting approval authority by accident. Define controller-disconnect and parent-exit behavior. [Result contract][stable-result-contract] · [task read][stable-task-read] · [task cancel][stable-task-cancel] · [recovery and delivery][stable-design]

An upstream operation could be added to the selected paired V2 WebSocket/HTTP boundary and use its environment session. That would not inherently require MCP OAuth. Exposing it through `/mcp` to an outside client would require a separately approved MCP OAuth lifecycle and a new caller authorization path; the current OAuth token cannot use `/ws` or HTTP and still has no parent thread. No extension is chosen here. [RPC audience][stable-oauth-audience] · [MCP middleware][stable-mcp-http] · [MCP caller guard][stable-caller-guard]

## Options for the later human decision

- Keep the chosen paired WS/HTTP first release to ordinary thread launch, send, read, wait, and interrupt. It already fits the external multi-instance boundary and does not claim child-task ownership. [RPC names][stable-rpc-names] · [launch contract][stable-wire-result]
- Use an explicitly launched T3 controller thread to *ask its agent* to delegate. This uses supported native parent ownership and needs no credential transfer, but provider behavior and parent lifecycle remain part of the workflow; it is not a direct controller task API. [External launch][stable-launch] · [native flow][stable-design]
- Seek a focused upstream external delegation contract. The human must choose whether that contract is paired-session WS/HTTP or separately authorized MCP OAuth, and whether the parent must be a live T3 agent run or may be a durable external owner. Decide the grant/revocation scope, result acknowledgement policy, and Stop/disconnect behavior before implementation. [RPC scope][stable-rpc-auth] · [MCP audience][stable-oauth-audience] · [delivery gate][stable-delivery-gate]

Do not adopt raw `delegated_task.request` as a standalone integration without that decision and upstream contract work. It is a public command shape and may create genuine child records against a live parent, but the inspected path does not provide the ownership, ceiling, and task lifecycle guarantees asked for here. [Command schema][stable-command] · [dispatcher][stable-low-level-dispatch] · [native mode check][stable-native-mode]

## Decisions still for a human

1. Is indirect delegation through an explicitly launched T3 agent enough for any later workflow, or must the standalone controller own create/status/cancel directly?
2. If direct ownership is required, should upstream authorize a verified live controller thread and run, or add a durable owner that does not depend on a provider run? What does parent Stop do to its children?
3. Should that later contract use the selected paired WS/HTTP session or a separately approved MCP OAuth client? What grant limits a controller to its own tasks, and what happens to those tasks after revocation or controller disconnect?
4. Which result acknowledgement, lost-response recovery, and cancellation guarantees must the external operation promise? A raw command sequence, passive projection read, and `thread.stop` do not answer these questions. [Wire result][stable-wire-result] · [task read][stable-task-read] · [task cancel][stable-task-cancel]

## Evidence limits

This report reads pinned first-party source and tests. It did not run those tests, pair with a live V2 instance, attempt the raw command, inspect running credentials or databases, or contact upstream maintainers. The low-level WebSocket conclusion is a code-path inference, not an observed wire exchange. The `main` comparison covers the cited delegation, access, RPC, and lifecycle paths at one immutable commit; it does not assert that every upstream file or future release is unchanged. No production source or decision record was changed.
