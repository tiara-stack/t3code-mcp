## External authentication and transport

T3Code still publishes `/.well-known/t3/environment` without a session. `environmentId` comes from a persisted file, whereas `serverVersion` describes the build and `orchestrationProtocolVersion` is `2`. An MCP instance registration can remain bound to the environment ID across endpoint or version changes, but it must test the target's identity and capabilities before use. The existing adapter already stores and checks that ID. [Descriptor contract][s-environment], [identity implementation][s-identity], [local registration][l-registration]

There are **two separate credential audiences** at stable `v0.1.2`:

1. A normal environment session uses a one-time pairing credential through `POST /oauth/token`, with requested scopes, or a browser session. It is accepted by authenticated HTTP and by `/ws` after `POST /api/auth/websocket-ticket`. `/ws` requires `?orchestrationProtocol=2` before it authenticates, then applies per-RPC scope checks. The V2 HTTP reads under `/api/orchestration/*` require `x-t3-orchestration-protocol: 2` and `orchestration:read`. [Token exchange][s-token-exchange], [HTTP endpoints][s-http-api], [HTTP header][s-http-header], [WS gate][s-ws-gate], [RPC policy][s-rpc-policy], [HTTP handlers][s-http-handlers]
2. `/mcp` accepts either a registry token minted for a T3-launched provider session or a separately approved MCP OAuth client token. It tries the registry first, then the MCP client authenticator. A normal paired environment bearer token fails the MCP client subject check; an MCP OAuth token is rejected by ordinary HTTP and WebSocket authentication. This is an implemented audience boundary, not merely a recommendation in the docs. [MCP middleware][s-mcp-http], [OAuth authenticator][s-mcp-client], [subject check][s-auth-mcp-client], [other-audience check][s-auth-audience], [transport test][s-mcp-http-test]

An outside agent can therefore call `/mcp`, but it must sign in to **each environment's** MCP OAuth server. Stable source publishes resource and authorization metadata, dynamic client registration, authorization-code PKCE, and an approval flow. A user approves with a qualifying one-time pairing code or an `access:write` browser session. The server issues a 30-day MCP client session. Approved access levels are `read-only`, `approval-required`, `auto-accept-edits`, `auto`, and `full-access`; read-only grants `orchestration:read`, normal write levels add `orchestration:operate`, and full access also grants `settings:write` and `source-control:write`. These are MCP access ceilings. They do not turn the OAuth token into an RPC token. [OAuth metadata/flow][s-mcp-oauth], [approval][s-oauth-approval], [access levels][s-mcp-access], [session implementation][s-auth-audience]

The MCP transport is HTTP at `/mcp` with protocol `2025-06-18`. Its test initializes a session, retains `mcp-session-id`, and sends `mcp-protocol-version: 2025-06-18` on the subsequent tool call. Use an MCP client implementation that follows this lifecycle rather than assuming a bare POST of a tool name is sufficient. [Transport registration][s-mcp-transport], [HTTP test][s-mcp-http-test]

The provider registry token is different again. The registry records environment, thread, provider instance, provider session, and capabilities, keeps only a hash of the raw token, expires it after 24 hours without a touch, and revokes it on session or thread release. The design document also mentions a maximum lifetime; this stable implementation shows an idle window and explicit revocation, not a separate absolute-age check in `resolve`. Do not infer a hard maximum lifetime from the document. [Registry implementation][s-mcp-registry], [revocation][s-mcp-revoke], [design note][s-mcp-design]

## Which native MCP operations an outside client can use

An OAuth caller has `client` authority and **no `thread` or parent run**. The handlers admit reads and ordinary thread operations within its approved runtime-mode ceiling. `orchestrator_capabilities` works, but its inherited parent, provider, model and options are null or empty. An outside caller supplies a project or thread ID when a tool would otherwise infer the calling thread. `t3_thread_launch` can start a top-level thread from an explicit project and model or project defaults, including root, existing worktree or new worktree strategies. `t3_thread_list`, `t3_thread_read`, `t3_thread_send`, `t3_thread_wait`, and `t3_thread_interrupt` use shared application services; writes to a thread above the caller's ceiling are refused. Read-only callers cannot write. [Invocation scope][s-invocation], [capabilities implementation][s-capabilities], [access guard][s-tool-access], [outside launch][s-outside-launch], [thread handlers][s-orch-handlers], [tests][s-tool-access-test]

`delegate_task`, `task_status`, `task_cancel`, `create_threads`, and other `actsAsCaller` handlers require the T3-launched provider-session thread credential. Delegation and batch creation additionally require an active parent run owned by that provider instance. A full-access OAuth client still receives `thread_credential_required`; it cannot synthesize a parent by passing a thread ID. Tests cover this distinction. The advertised feature flags in `orchestrator_capabilities` describe the server, so an external caller must filter them through its own caller type. [Handler declarations][s-orch-handlers], [delegate gate][s-delegate-gate], [caller guard][s-tool-access], [tests][s-tool-access-test]

`ThreadManagementService`, `ThreadMessageIntake`, and `OrchestratorV2` are app services inside T3Code, not a remotely callable service registry. `/mcp` and `/ws` share them through their handlers. The externally callable alternative to parent-scoped native tools is the normal environment session's V2 RPC, especially `orchestration.launchThread`, `orchestration.dispatchCommand`, and subscriptions. The HTTP API supplies bounded snapshot/history reads; it does not expose all V2 commands. A standalone multi-instance controller must keep one authenticated connection or MCP client per T3Code environment and add its own instance qualification. [MCP registration][s-mcp-registration], [WS dispatch][s-ws-dispatch], [V2 RPC schema][s-rpc-schemas], [HTTP API][s-http-api]

[V2 schemas][s-history-schema], [HTTP API][s-http-api], [page policy][s-paging] | `S`; history-preserving projection `U` |
| Execution and request IDs | Public `TurnReference = {instanceId, threadId, turnId}` and pending request IDs are keyed against V1 latest-turn/session state. [Run graph][s-run], [nodes][s-node], [provider turns][s-provider-turn], [shell][s-thread-shell] | `S`; historical ID reconciliation `U` |

Thread replay uses at most 128 events and 1 MiB raw plus 1 MiB projected encoded payload before it resets to a snapshot. Shell replay allows a 1,000-sequence gap and 8 MiB raw payload before resetting. The observer must treat replacement snapshots and unknown events as a possible history gap, not proof that a waited-for transition happened. These are limits in the stable implementation, not guarantees that all older events remain available. [Thread replay][s-thread-replay], [streaming][s-stream-impl], [shell replay][s-shell-replay], [shell check][s-shell-replay-check], [unknown-event schema][s-thread-stream]

`0.1.0`, `0.1.2`, the nightly, and `main` all declare protocol 2, but they have different source revisions. In particular the nightly/main add `getThreadFamily`, `getWorktreeThreadIds`, `getOlderSettledThreads`, and opt-in compact ID encoding; stable lacks them. Version 2 therefore requires capability and schema negotiation at the selected pin. Avoid designing against a `main` method while targeting stable. [Stable methods][s-rpc-schemas], [nightly methods][n-contract], [main methods][m-rpcs]

## Candidate integration boundaries and open questions

| Candidate | What the source supports | External-caller limit and question |
| --- | --- | --- |
| Pair each T3Code instance as a normal environment client, then use V2 WebSocket RPC plus HTTP reads | Preserves the current multi-instance registration model and access to command IDs, sequences, full projections, streaming subscriptions, and history pages. [WS policy][s-rpc-policy], [RPC schemas][s-rpc-schemas], [HTTP reads][s-http-api] | Requires new scopes, protocol-2 handshake, V2 codecs, and observer/correlation rewrite. Does Effect `4.0.0-rc.115` interoperate with T3Code's `4.0.5` RPC framing, or should the adapter upgrade its Effect version? `U`. |
| Pair an external MCP OAuth client per environment, then call native `/mcp` | Gives ordinary top-level launch, read, send, wait, interrupt, project/worktree tools, and the live provider catalog with a bounded authorization ceiling. [OAuth scope][s-mcp-oauth], [tool guards][s-tool-access], [launch][s-outside-launch] | Cannot call parent-scoped delegation/status/cancel/batch tools, and its token cannot use `/ws`/HTTP. MCP tools do not expose the complete V2 event stream or native receipt lookup. How should the controller preserve its own mutation receipts and exact waits if this is primary? `U`. |
| Hybrid native MCP operations plus a normal environment RPC/HTTP session | Can use equivalent native names where their external semantics fit, while retaining exact V2 observation from RPC/HTTP. [Native handlers][s-orch-handlers], [RPC methods][s-rpc-schemas] | Needs two credential lifecycles per environment and a deliberate mapping between MCP tool `clientRequestId` and local operation/command IDs. The two ingress paths may have different admission guarantees. Which operations, if any, merit this complexity? `U`. |
| Reuse `ThreadManagementService` or local `t3 thread` commands | They share application logic or operate on a host's local server. [Service boundary][s-mcp-design], [local CLI guidance][s-outside-doc] | Neither is a network API to several remote instances from this standalone process. An upstream API addition or in-process plugin would change the deployment model. |

The local SQLite store is separate from T3Code's `statev2.sqlite`. T3Code's own V1-to-V2 startup copy preserves *its* `state.sqlite` for lazy import; it does not migrate this MCP server's registrations, request keys, operation steps/evidence, captures, or retained turn evidence. This repository currently has schema version 7, and its registered credentials and mutation receipts live in distinct tables. Any upgrade plan must preserve those rows and their historical meanings while creating new V2 correlation, even if no V1 wire support remains. A saved V1 turn reference or command ID must not be silently recast as a V2 run. [T3Code DB import][s-db-import], [T3Code path][s-db-path], [local migrations][l-migrations], [local tables][l-schema], [turn evidence][l-evidence], [local default path][l-db-path]

Questions for the parent map and human decision are: choose the primary external ingress and target release/channel; decide whether OAuth sign-in is acceptable in addition to existing pairing; specify the new scope grant and re-pair path; define how old receipts/turn evidence remain queryable without replaying them as V2 mutations; and require disposable-instance interop checks for protocol framing, replay resets, launch outcomes, and identity binding. No live T3Code instance, credential, or database was used in this research.
